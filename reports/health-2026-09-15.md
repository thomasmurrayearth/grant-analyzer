## 7. Findings, ranked by damage

1. **The review keeps reading a stale local folder and mistaking it for the truth.** The snapshot mechanism was built so the review reads a committed file instead of a live call — but it reads the *local working copy*, which had not pulled from GitHub for 18 days. Cycle 4 saw the gap and wrongly concluded the pipeline had died; this cycle's first pass repeated it. The data was on `origin` the whole time. Until the review reads from `origin` (or the folder is pulled before it runs), a quiet local checkout will keep producing false blindness and false "pipeline dead" alarms. This is a measurement-integrity fault and it has now cost two cycles.
2. **The app has never captured whether its output is any good.** Zero feedback in 36 runs. The Phase 1 gate has no evidence and cannot get any until the feedback ask moves to where users act (the download click). Harms §1 and §3 directly.
3. **Retrieval is near-random between repeat runs** — Notpla 5 vs 10, Jaccard 0.071 on live per-item data. Confirms cycle 3's zero-convergence finding is not fixed; now evidenced with real output rather than counts.
4. **The shortlist still under-delivers against its own promise** — mean 6.5 of a promised 10, only one run of six reaching 10. `SHORTLIST_SIZE` is 10 (`analyzer.py:167`); Phase 3 researches 10 and the final scoring call publishes 4–10.
5. **Prompt caching is entirely off** (digest 09-14: cache tokens 0 across 29 calls). Avoidable spend at ~$0.60/run; not a quality issue. Watch-level.

Output quality itself is a finding in the good column: precision 1.000, 39/39 clean links, eligible shortlists with the major funders present.

New this cycle:

### Proposal 8 — Make the review read the snapshot from `origin`, not the local folder

- **Problem.** The review reads `reports/snapshots/` in the local working copy. When that copy has not pulled, the review silently sees stale data — and has now twice mistaken an unsynced folder for a dead pipeline (cycle 4, and this cycle's first pass).
- **Evidence.** GitHub held a snapshot for every September day; the local folder's newest was 28 August. Two cycles reported blind against data that existed the whole time.
- **What it fixes.** It removes the single biggest source of false blindness in the whole mechanism.
- **Options.** **(a)** Have `read_snapshots.py` fetch the newest snapshot from `origin` (raw GitHub URL — the committed file carries no secret) and fall back to local only if offline, labelling which it used. **(b)** Have the scheduled task run `git pull` on the snapshots path before reading. **(c)** Keep reading local, but make a staleness > 2 days a hard, loud failure that says "pull the folder" rather than "the pipeline is blind."
- **Recommendation: (a), with (c) as the fallback message.** (a) makes the review independent of local sync state entirely; (c) at minimum stops a stale folder masquerading as an outage.
- **Verification.** A deliberately un-pulled local folder still produces a correctly-measured cycle, or a message that names the real cause (unsynced folder) rather than "blind / pipeline dead."
