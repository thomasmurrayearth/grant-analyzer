New this cycle:

### Proposal 6 — Show a plain-English error instead of the raw server text

- **Problem.** On failure, `frontend/index.html:1334` prints the backend's
  error string verbatim; this fortnight that meant a Python type error shown
  to prospective clients, repeatedly.
- **Evidence.** 5 identical raw errors 28–29 Aug; one user retried 3 times;
  neither user returned.
- **Property harmed.** The credibility test, and §1 directly.
- **Options.** **(a)** Generic friendly message + retry suggestion, full detail
  still logged to Supabase (an hour's work). **(b)** As (a) plus an email to
  Thomas on every failed run, so the next outage is known in minutes.
- **Recommendation: (b).** At two users a week, losing both to an error screen
  is the single most expensive thing the app did this fortnight.
- **Verification.** Next failed run in Supabase shows the logged technical
  error while no raw exception text appears in the frontend; Thomas receives
  the notification.

### Proposal 7 — Pin everything, and make the watchdog bark

- **Problem.** One dependency was pinned in the emergency fix; the rest of
  `requirements.txt` can still drift under the app on any rebuild. And the
  snapshot workflow fails silently — it neither alerted on the outage nor on
  its own death.
- **Options.** **(a)** Pin all versions in `requirements.txt` exactly
  (`pip freeze` from the known-good build) and add a workflow step that opens
  a GitHub issue (which emails Thomas) when the health check fails or the
  snapshot cannot be committed. **(b)** Pins only.
- **Recommendation: (a).** Both halves are cheap; together they close the
  class of failure, not just this instance. Touches nothing a user sees, but
  changing CI needs GitHub access this session does not have, so it is
  proposed rather than done.
- **Verification.** A deliberately failing health check produces an issue
  within a day; `pip install -r requirements.txt` resolves identically on two
  consecutive rebuilds.
